# ADR-0012: 让「未归组内容」可见可归，并堵住永久隐身

## 日期

2026-10-20

## 状态

已采纳

## 背景

生产实测（2026-10-20，`news.myaicode.qzz.io`）：

| 指标              | github | producthunt | twitter |
| ----------------- | ------ | ----------- | ------- |
| raw_items 总数    | 365    | 2119        | 1722    |
| 徽标显示的未读数  | **8**  | 851         | 306     |
| topic_groups 组数 | **0**  | 325         | 50      |
| 组内条目数        | **0**  | 961         | 301     |

现象：GitHub 标签显示「8」，点进去整页「暂无数据」；而这 8 条在归档页
也找不到（归档页只收已读条目）。**全站唯一能看见它们的地方就是徽标数字。**

根因是三个缺陷叠加：

1. **两套口径**：徽标按 `raw_items` 的未读行数计数（`getNewsCounts`），
   列表按 `topic_groups` 渲染（`getTopicGroupMeta`）。任何"已入库、未落组"的
   条目都会表现为「有数字、没内容」。
2. **落组失败被"假消费"**：`storeTopicGroups` 此前返回 `void`，调用方只能把
   **整批**都标记为已聚合（`topic-aggregate.ts` 的 `consumedIds.push(...sub.map(...))`）。
   于是 AI 漏掉的、或 id 对不上的条目既不在任何组里（前台看不见），
   又已被 `aggregated_at` 标记为已消费 —— 而聚合队列只捞 `aggregated_at IS NULL`，
   这些内容**永远不会再被聚合**。线上 github 365 条、PH 44 条、Twitter 19 条全是这种状态。
3. **低频源被阈值饿死**：`generateTopicAggregation` 与聚合脚本都要求
   **至少 3 条**才聚类，而 GitHub 每天净增只有 2-4 条 —— 永远凑不满，
   主题组长期为 0（Enrich 日志原文：`Found 2 pending items → Not enough items to aggregate (< 3), skip`）。

补一刀：id 匹配是大小写敏感的，而 GitHub 的 id 已按 ADR-0006 归一化为小写，
AI 却常照抄标题里的原始大小写（`github:deepseek-ai/DeepGEMM`）——
这类条目 100% 对不上，被 `⚠️ Skipping invalid itemId` 静默跳过。

最后，「读完即物理删组」（`/api/news` 的 read/readGroup/readAll）
让已读条目的组彻底消失 —— 已读内容因此无法回看（这与本 ADR 无关，
但它制造了"读完之后内容彻底不存在"的观感）。

## 决策

**「已入库未归组」的内容必须既看得见、也能被归组。**

### 1. 未归组内容显式渲染（前台）

- `GET /api/news/ungrouped`：返回**未读且不在任何主题组里**的条目
  （含 `pendingSummary` 标记：还没生成 AI 摘要）
- 首页新增「待归组内容」分组（`src/app/components/PendingItems.tsx`）：
  折叠头写明条数与成因（待摘要 / 待归组），展开后逐条列出、点开懒加载详情
- 徽标数字口径**不变**（仍是 raw_items 未读数），但标签上加 `title`
  写明构成（"8 条未读，其中 8 条待归组"），并用一枚琥珀色圆点标记
- 空状态只在「既无主题组、又无待归组内容」时出现

### 2. 落组结果可观测（后端）

- `storeTopicGroups` 改为返回 `{ linked, skipped }`：
  只有**真正挂进某个组**的条目才算 `linked`
- 聚合脚本只把 `linked` 标记为已聚合；未落组的保持 pending，下轮重试
- id 匹配增强：大小写不敏感 + 按标题回退（标题唯一命中才采用）

### 3. 解除低频源阈值

- 聚类阈值从 3 降到 **1**：1 条内容也要聚类
- 小批量（1-2 条）且 AI 返回空时，**兜底建组**
  （`buildFallbackGroup`），不再让条目悬空

### 4. 可展示性巡检（防复发）

- `scripts/check-visibility.ts` + `src/lib/visibility.ts`：
  某源「有未读内容却一个主题组都没有」→ 立即告警；
  未归组内容卡住超过 24h → 告警
- 新增 workflow `Content Visibility Check`（每天 3 次 → 红 → Sentry 通知）
- 补齐巡检盲区：原有 `check-freshness` 只看「最后入库时间」，
  数据天天有入库时它永远绿，永远发现不了"有数字、没内容"

### 5. 存量补救

- `scripts/requeue-ungrouped.ts`：把「未读且未归组」的条目的 `aggregated_at`
  置回 NULL，重新放回聚合队列
- **默认只处理未读**：已读条目按产品语义「读完即消失」，不重新冒出来

## 备选（已拒绝）

- **改徽标口径为「组内未读」**：数字与内容严格自洽，但用户会看到
  "徽标 0、页面却有 8 条"，反而更困惑；且它掩盖了"抓到了却没展示"这一事实
- **不渲染待归组内容，只在空状态写一句说明**：仍然"数字有、内容无"，
  用户永远读不到那 8 条
- **自动删除未归组内容**：内容已入库（付了 AI 成本），删除等于丢数据
- **保留「至少 3 条」阈值**：低频源永远长不出主题组，正是本次事故的土壤
- **恢复已读条目的主题组**：已读内容按用户口径"读完了"，
  重新冒出来会打扰；且已读条目 357 条，恢复它们的组没有收益

## 后果

- 徽标上的每个数字都能在页面里找到对应内容（前台 + e2e 双层回归防线）
- 未落组的条目不再永久隐身：保持 pending、下轮重试，兜底建组
- 新增一轮巡检，把"能抓到但展示不出来"变成会报警的故障，而不是沉默
- 代价：首页多一次 `getUngroupedItems` 查询（线上 71 条，毫秒级）；
  聚合队列里会多出一批"反复重试"的条目（AI 持续漏掉的少数条目），
  由可展示性巡检兜底告警
