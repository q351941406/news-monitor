# ADR-0009: 拆分抓取与富化（摘要 / 聚合）

## 日期

2026-09-25

## 状态

已采纳

## 背景

原编排：每个 scrape workflow 通过 composite action 依次执行
**抓取 → AI 摘要 → 主题聚合**，三件事在一次运行里完成。

暴露出的问题：

1. **失败归因错位**：AI 失败会让整个 run 变红，而 `scrape-guard` 的告警文案是「抓取失败」
   —— 但抓取其实成功了。维护者看到的是误导性信息。
2. **外部依赖性质不同**：抓取依赖站点（改版 / 限流），富化依赖 LLM（慢 / 贵 / 易超时）。
3. **频率需求不同**：内容不需要实时可见，AI 调用次数本可以远少于抓取次数。
4. **调试不便**：想单独重跑 AI 就得重新抓取（重复抓取、重复计费）。
5. **超时风险**：三件事共享同一个 timeout 预算。

## 决策

**抓取只负责写入 `raw_items`；富化（摘要 + 聚合）独立调度。**

```
scrape-github.yml      (每天 13:00 UTC)  ┐
scrape-twitter.yml     (每天 03:30 UTC)  ├─▶ raw_items（原始内容）
scrape-producthunt.yml (每 6 小时)       ┘
                                             │
                            enrich.yml (每天 19:00 UTC)
                                             ▼
                                 ai_analysis + topic_groups
```

| 职责 | workflow       | 需要的凭据                                      |
| ---- | -------------- | ----------------------------------------------- |
| 抓取 | `scrape-*.yml` | 数据源凭据（`PRODUCTHUNT_TOKEN` / `TWITTER_*`） |
| 富化 | `enrich.yml`   | 只需 AI 凭据                                    |

### 配套改造（不做这些则拆分不成立）

1. `ai-process.ts` / `topic-aggregate.ts` 支持 `--source=all`
2. 两者改为**循环消费**（`scripts/drain.ts`）—— 拆分后单次运行要消化「一天累积的积压」
   （约数十条），而单批只取 50 条，不循环就永远追不上
3. 源列表从 `src/sources` 派生，不硬编码（新增数据源自动覆盖）

### 调度选择

`enrich.yml` 排在 **UTC 19:00** —— 晚于 PH 当天最后一次抓取（18:30），
一次覆盖三个源当天的全部结果。内容可见性延迟最大约 18.5 小时（PH 00:30 抓取的那批），
维护者明确表示不需要实时。

## 影响

- 正面：**告警归因准确** —— 抓取失败与 AI 失败不再混为一谈
- 正面：AI 调用频率独立可控，从「随抓取触发（每天 4+N 次）」降到「每天 1 次」
- 正面：可单独重跑富化而不重复抓取（调试、补数据）
- 正面：富化不需要任何数据源凭据，权限面更小
- **代价：内容可见性延迟**。首页由主题组驱动，抓取到聚合之间新内容不出现在首页
- 代价：积压可能跨轮累积。富化连续失败时队列增长（`aggregated_at IS NULL`），
  恢复后由循环消费追平；单次运行上限 20 轮 × 50 条 = 1000 条/源
- 风险：富化**没有**自动重试（scrape workflows 有 retry）。依赖 Sentry 告警 + 次日定时兜底

## 备选方案

- **保持耦合**：失败归因问题无法解决，且 AI 成本随抓取频率线性增长。未采用
- **用 `workflow_run` 在抓取后自动触发富化**：等于又耦合回去，且抓取频繁时富化会被触发多次，
  失去「AI 频率可控」这一主要收益。未采用
- **把聚合再拆成第三个 workflow**：摘要与聚合有严格顺序依赖（聚合只取已有摘要的条目），
  且同属「富化」这一关注点，再拆只增加编排复杂度。未采用
